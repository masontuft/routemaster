# Changelog

All notable changes are recorded here, following [Keep a Changelog](https://keepachangelog.com/).

## Unreleased

### Fixed
- Review fixes on rebooking: penciling in checks on the server that a customer is in the not-yet-booked group (a forged form can no longer pencil in a never-served or declined customer), and a customer's own request takes the same row lock so the two cannot both book the same year. A saved route that holds tentative stops is shown as out of date, without its table or map links, while the option is off, and any route goes out of date when a stop's map point is cleared or found again (for example after an area's city changes). The schema reference now lists migrations through 023, and the roadmap marks rebooking as built.
- The form parser now accepts up to 5,000 fields (it stopped at 1,000), so ticking about 1,000 or more customers on the rebooking page is no longer rejected with a 413 error.

### Added
- Making links for all areas on the rebooking page now makes one batch per area, so a selection over 500 customers is no longer refused. A customer belongs to the area of their first property (the lowest id), so one with properties in two areas is linked once. Customers whose first property has no area form a "No area" batch. Each batch is its own transaction and records its area; an area that fails is listed and the rest are kept. The result page has a section and a CSV download for each area. Property type (residence, rental, second home) is on the roadmap as the better way to choose.
- Rebooking: `/staff/rebooking` sorts the customers in an area into not yet booked, declined, never served and already booked for a chosen year, with the last service date and whether a link was made. Staff tick customers and make links for just those, using the same one-time link page as a batch. A year is the year of the day a request was booked for, and a job completed this year counts as booked.
- The rebooking page has an "All areas" choice (every customer with a property, in any area or none), and Select All and Clear buttons for each group. Select All ticks only customers with a phone that can be texted. The buttons are plain progressive enhancement from `public/js/rebooking.js`, so the page still works without scripts, and the content security policy is unchanged. A count shows how many are ticked and, for one area, warns above the 500-link batch limit.
- Penciling in: with the new owner option on (`/admin/settings`, off by default), the day board lists customers in areas worked that day who were served before and have nothing booked that year, and books the ticked ones as tentative Scheduled requests. The customer sees "Please Confirm Your Day" and can confirm, choose a different day (which returns the request to Requested) or decline. Staff can mark a booking confirmed. The route builder includes tentative stops only while the option is on, and marks them. Migration 022 adds `app_settings` and `service_requests.tentative`.
- Areas can have a city (migration 023, set for many areas at once at `/staff/areas`). A property with no city is looked up on the map, and shown on the route, with its area's city. Changing an area's city sends its city-less properties back to be looked up.
- A living process doc, `docs/process/customer-lifecycle.md`, describes the customer process from import to route. A test (`src/processDoc.test.js`) fails when a page named in it is not a route, or when a route in a process area is not in it. `AGENTS.md` tells agents to update it with any change to the process.
- `pnpm seed:test` fills the local test database with sample data: 8 made-up customers, two areas with days, requests in every status, and a built route for tomorrow. It only runs against `TEST_DATABASE_URL`, and `--reset` rebuilds it. `pnpm dev:test` runs the app against that database.from scratch.
- Owners and dispatchers can build a day's route (`/staff/routes`). Pick a day, find a map point for each booked address (Google when a key is set, then OpenStreetMap), fix any address that cannot be found, then build. The stops are ordered with nearest-neighbor plus a 2-opt improvement, timed from a start time with a set number of minutes at each stop, and saved with the day (migrations 020 and 021: `properties.latitude`, `longitude`, `geocode_status`; `routes` and `route_stops`). The page shows each stop with its arrival time, phone and notes, the total miles and drive time, and Google Maps links split into parts for long days. It warns when the day's booked jobs have changed since the route was built. The ordering is a JavaScript port of `route_optimizer.py` from the TSB project, with the 2-opt step added and the hardcoded home address and key removed (`GOOGLE_MAPS_API_KEY`, `SERVICE_STATE` and `ROUTE_START_ADDRESS` are optional settings).
- Owners and dispatchers can book a whole day's requests at once on the day board (`/staff/day-board`). Pick a day, see who asked for it grouped by area and street, tick the customers to visit, and book them. It uses the same status change as a single request, books only requests still in Requested, and skips the rest.
- Owners and dispatchers can make scheduling links for a whole area at once (`/staff/link-batches/new`). Pick an area, preview the counts, and the app makes one link per customer with a property there and a phone that can be texted, then shows a table and CSV of name, phone and message to copy into a texting tool. Nothing is sent. By default a customer who already has a working link is skipped. Customers without a usable phone are listed with a link to fix them. The links are shown only on that response, and each run is recorded in `link_batches` with who ran it, the area, the lifetime and the counts (migration 019). A batch holds at most 500 links and a lifetime of 1 to 120 days.
- Staff can assign days to areas, and customers choose from their area's days. `/staff/areas` creates and renames areas and adds days to them, one date at a time or every chosen weekday between two dates (migration 018, `area_days`). Each date is stored on its own so any one can be removed. The property edit page has an Area field. On a customer's new-request and change-request pages, the date is a list of the days for that property's area, and the server refuses a date outside the list. A property with no area, or an area with no upcoming days, can still send a request: the date is shown as a preference, not a confirmed time, and staff choose the day. The public `/schedule` page is unchanged and still takes any date, because showing area days there would reveal whether a visitor is a customer. Staff can still schedule any day.
- Owners can delete a customer (`/staff/customers/:id/delete`) and clear customers in bulk (`/admin/clear`): by import batch, which removes the customers that batch created, or all customers behind a typed phrase. Each delete first shows the exact counts of customers, properties, requests, reviews and links that go with it, and a bulk delete is refused if those counts changed before it runs. There is no undo. Staff logins, import batches and service types are kept.
- Owners and dispatchers can edit a customer's details and a property's city, ZIP and notes from the staff pages, add a property to a customer, and filter the customer list to those with a property missing a city. Only an owner can change a name or a street, because matching reads them; the route refuses a posted field the role may not change, not just the form. Normalized name, phone and address are recomputed on every edit.
- A spreadsheet import no longer skips a row for lacking a city. The street is saved, the property's city is left empty (migration 017 drops `NOT NULL` on `properties.city`), and the preview and result page say how many properties have no city. Lists show just the street for those. Properties made by hand still require a city. The import page now asks for a name, street, city and ZIP on every row.
- Staff and owners can record who referred a job. `service_requests.referred_by` (migration 015) stores the name only. Referral payouts are handled outside the app.
- Owners can paste a public Google Sheet link at `/admin/import` and see each tab with its row and column counts. Nothing is saved yet. A zip that declares more than 50 MiB uncompressed or 200 entries is refused before parsing.
- Owners can confirm a spreadsheet import. The preview now takes a service type, a status and a default city, and a Confirm Import button writes the new customers, properties and past jobs in one transaction. A changed sheet or database refuses and writes nothing; confirming the same sheet twice changes nothing; imported jobs are dated by their own day. Migration 016 adds `import_batches`, `import_mappings`, `subdivisions`, `service_requests.amount_cents`, and an `import_batch_id` on customers, properties and service requests.
- Owners can pick a tab at `/admin/import`, map its columns (with a header row and a season year), and see a read-only preview: rows that are new, already on file, at a new street for a known customer, flagged because the street belongs to someone else, or cannot be imported. Nothing is saved. The import pages are never cached.
- Spreadsheet import spike: download a public Google Sheet from a fixed `docs.google.com` export URL, and parse `.xlsx` rows with ExcelJS 4.4.0, with size and row limits (`src/import/`). No import screen yet.
- Deploy preparation: database-aware `/health`, pool error handling, a production `SESSION_SECRET` check, hand-written security headers, `render.yaml`, and a deployment runbook.
- Roadmap entry for branded business workspaces: a planned, uncommitted sign-up where each business gets a workspace and a branded mirror of the service sign-up, plus a customization layer. Open questions are marked `TODO (Mason)`.
- Futuristic marketing pages: home ("Schedule Your Service" hero and tiles), a public services and pricing page, and the contact page in the same layout; over-the-top 404 and error pages; Services nav link (the owner link is now "Manage Services").
- Styling foundation: enterprise palette tokens with light and dark, a conservative base for every app page, cascade-layered CSS, a skip link, safe-area padding, scrolling table regions, and a test that checks view headings against modified Chicago case.
- Customer reviews of completed jobs, a public reviews page, a contact form, and staff moderation (hide, restore, owner delete) and message replies (migrations 013 and 014).
- Owner admin: manage users and roles, create staff users, edit the service catalog and prices, and owner-only monthly numbers on the staff dashboard.
- `pnpm dev` watches `src/` and `public/` with Node's `--watch` and reloads the open page after the server restarts. The script sets `NODE_ENV=development` so a production value in `.env` cannot disable the reload.
- Staff dashboard for owners and dispatchers: request queue, status transitions with history, Needs Review matching, customer search, and link creation and revocation (migration 012).
- Architecture overview, ADRs 0001 to 0011, and the `docs/` tree.
- Contributing guide, security policy and issue and pull request templates.
- `package.json`, ESLint config, `node:test` runner, the `TEST_DATABASE_URL` guard with tests, and a GitHub Actions CI workflow.

- Customer service requests with status history, properties, magic and generic scheduling links, and rate limiting with express-rate-limit (migrations 004 to 011, ADR 0012).
- Authentication: register, login, logout, Postgres-backed sessions, CSRF protection, role middleware, bcrypt hashing, and `pnpm seed` for test accounts.
- Migration runner (`src/db/migrate.js`, `pnpm migrate`) with `roles` and `users` migrations, tested against the throwaway database; CI gets a Postgres service container.
- Express app skeleton: `src/app.js`, `src/server.js`, `/` and `/health` routes, 404 and error pages, global error handler, and supertest tests.

### Fixed

- README no longer says the server is unwritten and that `pnpm start` fails.
- `devReload` treats `NODE_ENV` as production after trim and case-fold, so `Production` or padded values do not leave `/__dev/boot` enabled.
- The system context diagram renders on GitHub. Dotted edge labels that contained periods now use the pipe form.
- The test-database guard treats connection strings that name the same host, port, and database as the same database.
- Setup docs that still said `package.json`, `.node-version`, or CI did not exist.

### Security

- `minimatch` is overridden to `^11.0.1` so the ESLint 10 tree is not on the release named by GHSA-g3hv-75wg-m249. Remove the override once ESLint depends on a patched `minimatch`.
- The test-database guard treats `localhost`, `127.0.0.1`, and `::1` (including bracketed `[::1]`) as the same server.
- A pasted Google Sheet link cannot choose the download host. Redirects stay on Google's export path, cookies are not forwarded, and a body over 5 MiB is refused.
- A cosmetic difference in `TEST_DATABASE_URL` (scheme, default port, credentials, trailing slash, or an ignored query parameter) can no longer point tests at the real database.
