## Name rules, segment 1: the pure functions

- **Changed:** `src/utils/personName.js` (new: `tidyName`, `normalizePersonName`, `extractRental`, `classifyName`), `src/utils/personName.test.js` (new, 19 tests), this file. Branch `feat/name-normalization-rules`, from `main` at c0adfa7. Nothing imports the new module yet, so the app behaves as before.
- **Why:** `normalizeName` turns every non-alphanumeric character into a space, so "Sam & Ruth Example" and "Sam and Ruth Example" got different match keys, and "O'Brien" became "o brien". Segment 1 of the plan writes the rules and tests them before anything uses them.
- **Decisions:** A joint name is one customer and is never flagged. `&`, "and" and a slash between two words of two letters or more give the same key. An apostrophe or period is removed, a hyphen or comma is a space, Jr and Sr stay in the key. `classifyName` returns `status` ok, note or review, plus `name`, `rental` and `reasons` (each with `blocks`). One word is a note, so the row still imports; every other reason is review, so the row is skipped (option A). A "rental" note is taken out of a real person's name and returned as `rental: true` for the later property-type work. A possessive ('s) is flagged as a note about a relative. The word lists came from a research agent and a scan of the 992 real customer names, read-only (kept out of the repo, since they print names): the agent's roughly 120 candidate words matched only "hoa", "associates" and "neighbor", and none flagged a real customer wrongly. Left out as surnames: ward, park, hill, king, hall, price, co, blank, lot, living. `normalizeName` is untouched, because areas still use it. Dropping marks on letters ("José" is "jose") was my addition, not in the approved table.
- **Open / next:** Segment 2 wires `normalizePersonName` and `extractRental` into `customer.js` and the import files, and adds the `scripts/renormalize-customer-names.js` backfill with `--dry-run`. On the real data the new rules give 893 ok, 82 note (one word) and 17 review, 3 rental hints, and 96 of 992 keys would change; the 17 skipped names are all odd (relatives, businesses, parentheses, a phone number). Until the backfill runs, existing keys differ from new ones. The Utah entity forms rest on secondary guides and the Idaho rules were read through a fetch summary, so verify them. Verified: the new test file passes (19 of 19) and `pnpm lint` is clean. The full suite was not run, because it needs `TEST_DATABASE_URL` and no code path uses the new module yet.
