## Make the database ERD, and keep it from going stale

- **Changed:** `docs/architecture/database-erd.md` (new, Mermaid ERD), `src/db/erd.js` (new: `readSchema`, `buildMermaid`, `readDiagramBlock`, `writeDiagramBlock`), `scripts/generate-erd.js` (new), `package.json` (`erd`), `src/schemaDocs.test.js` (new, 6 tests), `README.md` and `docs/architecture/diagrams/README.md` (stale "migrations 001 through 023 / 014" lines replaced with links), `CHANGELOG.md`, this file. Branch `docs/schema-erd`, from `main` at c0adfa7. No schema change.
- **Why:** Mason asked that the ERD be up to date and that a FigJam board match it. There was no ERD in the repo, only a column list, two docs gave stale migration counts, and the FigJam board I made earlier showed `users.name`, `property_type` and `leads`, which were never built.
- **Decisions:** The diagram is generated from the migrations, not drawn: `pnpm erd` migrates a throwaway schema in `TEST_DATABASE_URL`, reads tables, keys and foreign keys, and rewrites the block between `erd:start` and `erd:end`. `schemaDocs.test.js` fails if that block, or the column lists in `RouteMaster-Database-Schema.md`, differ from the migrations. Cardinality comes from the real keys: a not-null foreign key is "exactly one", a nullable one "zero or one", and a unique one "zero or one" on the child side. Entities show only primary and foreign key columns, and tables with no relationship (`schema_migrations`, `session`) are left out. The FigJam board "Routemaster database ERD (from migrations)" was built from the same text and is linked from the doc; it is a copy and nothing updates it.
- **Open / next:** The old FigJam board "Routemaster schema changes (proposed)" (id 1IkTGQ21vinxQ5lNMIu0fD) still exists; I cannot delete it, so Mason should. The FigJam layout and the Mermaid rendering on GitHub were not looked at. The schema reference file is still produced by a tool outside the repo, so the test can only say it is stale, not fix it. This branch and `feat/name-normalization-rules` both append to this ledger file and edit `CHANGELOG.md`, so whichever merges second will have a small conflict.
