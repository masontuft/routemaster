## All areas: one batch per area

- **Changed:** `src/models/linkBatch.js` (`groupByOwningArea`, `createForAllAreas`), `src/controllers/linkBatches.js` (`renderResults`, `renderResult` now wraps it), `src/controllers/rebooking.js`, `src/views/staff/link-batch-result.ejs` (a section per area, a failed list), `src/views/staff/rebooking.ejs` (no `data-limit` for all areas), `src/app.js` (`parameterLimit: 5000`), tests `linkBatch`, `linkBatchPages`, `rebookingPages`; roadmap (property type), process doc step 9, changelog, threat model, known limitations. Branch `feat/rebooking`, on PR #57.
- **Why:** Mason's real sheet has 1,189 customers to rebook and a batch holds 500. Mason proposed splitting the All areas run by area and chose the customer's first property to decide the area when a customer has several; a residence indicator went on the roadmap.
- **Decisions:** First property means lowest id, chosen in one SQL `DISTINCT ON`, so a later property type changes one ORDER BY. Each area reuses `create` unchanged, in its own transaction; a failed area is reported and the rest kept, because tokens are only shown once. The cap stays for a single area. Found while testing: the form parser rejected more than 1,000 fields, which ticking about 1,000 customers would have hit, so the limit was raised to 5,000.
- **Open / next:** The 98 areas came from a free-text column, so the result page may be long. A failed area has no record except the page and a log line; the remedy is to run All areas again. Not yet seen in a browser. A landlord may be linked under a rental's area until property type exists.
