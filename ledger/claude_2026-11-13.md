## Fail fast when the database does not answer

- **Changed:** `src/db/pool.js` (new `createStartupPool` with a 10 second `connectionTimeoutMillis`, constant `CONNECTION_TIMEOUT_MS`; `createPool` is unchanged), `scripts/migrate.js` (uses `createStartupPool`), `src/deploy.test.js` (two tests), this file. Branch `fix/pool-connection-timeout`, from `main` at 78df1d1. PR #64.
- **Why:** The Render deploy of 78df1d1 built, then timed out after 15 minutes with no start-command or app output. `pg.Pool` waits forever for a connection, so a database that accepts the socket and never answers would hang `pnpm migrate` and keep `pnpm start` from running. Cause of that deploy is not confirmed; this makes the next one fail in seconds with an error in the logs.
- **Decisions:** 10 seconds (Mason's choice), a constant and not an environment variable. First version set it on every pool; after review Mason chose to apply it only to the migrate pool, so a request waiting for a free client in the running app is not cut off. `server.js` makes no database connection before it listens, so there is no startup pool there to bound. Chose a connection timeout, not `statement_timeout`, because a migration may run long. No retry loop, since it hides the failure.
- **Open / next:** A paused or cold Supabase project that takes over 10 seconds to answer now fails the deploy; a redeploy fixes it. Whether Supabase was paused on 2026-11-10 is unchecked. A keep-alive ping for the free plan's inactivity pause is discussed, not built. The app's own pool still waits forever for a connection, so a database that hangs after boot would hang requests. Verified: `pnpm lint` clean, `pnpm test` 499 of 499 against `TEST_DATABASE_URL`, and `node scripts/migrate.js` against a local server that never answers exits 1 after 10 seconds with "Connection terminated due to connection timeout".
