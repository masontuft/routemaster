## Leads table, segment 1: the table, the backfill and the model

- **Changed:** `migrations/025_create_leads.sql` (new `leads` table, `service_requests.lead_id`, a backfill from the `contact_*` columns), `src/models/lead.js` (new: `findOrCreate`, `findById`, `markConverted`), tests in `src/models/lead.test.js` and `src/db/leadBackfill.test.js`, `src/db/migrate.test.js` (one more file name), `docs/architecture/RouteMaster-Database-Schema.md` (by hand) and `database-erd.md` (`pnpm erd`), this file. Branch `feat/leads-table`.
- **Why:** Mason noticed the ERD had no leads table and that the typed name and contact details on a request repeat when the same person asks twice. The `contact_*` columns are filled only for Needs Review requests (a `/schedule` visitor who matched no customer), so a visitor who does not match and asks twice has their details copied onto both requests and staff match each by hand.
- **Decisions:** (1) The address lives on the lead, so the lead key is name, phone and street together, as `/schedule` matches today. One person at two addresses is two leads. (2) Email is left out because the public form does not collect it. (3) Expand and contract: 025 keeps the `contact_*` columns and the CHECK accepts either shape, so the suite stays green and old and new code both work during a deploy. A later migration drops the columns once nothing reads them. (4) A request that was already matched also gets a lead from its typed details, marked converted to its customer, so the typed text is not lost when the columns go. (5) The match keys for backfilled leads are worked out in SQL, because a migration cannot call the JavaScript in `src/utils`. They follow `personKey`, `normalizePhone` and `normalizeAddress` except for letters with accents. A test compares them with the JavaScript. (6) `findOrCreate` uses `ON CONFLICT ... DO UPDATE SET name = leads.name` so two simultaneous submissions make one lead.
- **Open / next:** Segment 2 wires `/schedule` and the staff pages to leads, converts all of a lead's open Needs Review requests when one is matched, and adds the migration that drops `contact_*`. Segment 3 is the docs (process doc, known limitations, a Proposed ADR 0017), changelog and this ledger. `pnpm names:renormalize` does not cover leads yet. Not run against the live database: the backfill will run on deploy through `pnpm migrate`, so the live Needs Review count and any odd typed names are unchecked. Verified on the test database: the full suite passes (552 of 552) and `pnpm lint` is clean. Nothing is committed yet.

## Leads table, segment 2: the public form and the staff pages use leads

- **Changed:** `migrations/026_drop_request_contact_columns.sql` (drops `contact_name`, `contact_phone`, `contact_address` and tightens the CHECK to "matched, or unmatched with a lead"), `src/controllers/schedule.js` (no match: `Lead.findOrCreate`, then the request gets `leadId`), `src/models/serviceRequest.js` (`create` takes `leadId`, not `contact`), `src/models/staff.js` (queries read the lead; matching converts the lead), `src/controllers/staff.js`, `src/views/staff/match.ejs` and `request.ejs`, schema reference (columns removed), tests in `src/staff.test.js`, `src/requests.test.js`, `src/models/models.test.js`, `src/rebooking.test.js`, `src/db/leadBackfill.test.js` and `src/db/migrate.test.js`. Same branch, nothing committed.
- **Why:** Segment 1 made the table. Now nothing reads the typed columns, so they go, and a visitor who asks twice keeps one lead.
- **Decisions:** (1) Matching one request, to a new customer or an existing property, matches the lead's other Needs Review requests to the same customer and property and marks the lead converted. A cancelled request is left alone. The match page says how many others will be matched. (2) Lock order: the lead row first, then the request rows. Two staff matching different requests of one lead queue on the lead; locking requests first could deadlock. A test fires both at once. (3) The new CHECK in 026 runs against every existing row, so the migration fails and rolls back if any unmatched request has no lead. A test shows that. (4) The lead is made in a separate statement from the request, so a failure between them leaves a lead with no request. It is harmless and the next submission reuses it.
- **Open / next:** Segment 3 is the docs (process doc and its changes table, known limitations, a Proposed ADR 0017, changelog, `docs/architecture/database-erd.md` is already regenerated). The FigJam copy of the ERD is stale. The match page's "typed by the visitor" text is read-only, as before. Verified on the test database: the full suite passes (559 of 559) and `pnpm lint` is clean. Several tests, including ones this branch does not touch, took over ten minutes each in the last run because the machine was under load; nothing failed. Not tried in a browser.

## Leads table: a lead goes with its customer

- **Changed:** `migrations/027_leads_go_with_their_customer.sql` (`leads.customer_id` becomes `ON DELETE CASCADE`, `service_requests.lead_id` becomes `ON DELETE SET NULL`), `src/models/customer.js` (`remove` is now a transaction, `clear` and `remove` first delete the unmatched requests of the leads about to go, `countRelated` and `countClearScope` count `leads` and include those requests in `requests`), `src/controllers/clear.js`, `src/views/admin/clear-confirm.ejs`, `clear.ejs`, `src/views/staff/customer-delete.ejs`, new `src/leadDelete.test.js` (6 tests), `src/customerClear.test.js` and `src/db/migrate.test.js`, plus ADR 0017, the process doc, known limitations, the threat model, `ARCHITECTURE.md`, the changelog and this file. Same branch, nothing committed.
- **Why:** Mason said to fix the regression the segment 3 entry flagged: deleting a customer kept the name, phone and street they typed, on the lead.
- **Decisions:** `lead_id` is `SET NULL`, not `CASCADE`: a lead can have requests matched to a different customer (a person who moved, or one lead matched by hand to two customers), and deleting one customer must not delete another's request. An unmatched request needs its lead (the CHECK), so the delete code removes those first; a delete path that forgets fails on the CHECK, and a test shows that. A visitor who never became a customer keeps their lead and request, as unmatched requests always have. The delete pages show the lead count, and the bulk delete's refusal when counts changed covers it.
- **Open / next:** A delete racing a new request on the same converted lead can fail on the CHECK and roll back, so it can be repeated. The delete pages were not looked at in a browser. The earlier open items stand: the live backfill is unseen, `pnpm names:renormalize` does not cover leads, the FigJam ERD copy is stale. Verified on the test database: `src/leadDelete.test.js`, `src/customerClear.test.js`, `src/customerDelete.test.js`, `src/db/migrate.test.js` and `src/schemaDocs.test.js` pass and `pnpm lint` is clean; the full suite passed 565 of 565 after one segment 1 test was updated to the new delete rule.
