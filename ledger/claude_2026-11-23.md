## New area from the property edit page

- **Changed:** `src/views/staff/property-edit.ejs` (the first option is now "No area/Other", a New Area field in a `data-new-area` wrapper, and a script tag); `src/controllers/staff.js` `updateProperty`; `src/utils/permissions.js` (`newAreaName` for owner and dispatcher); new `public/js/propertyArea.js`; tests `tests/propertyNewArea.test.js` (8) and `tests/propertyAreaScript.test.js` (2); `docs/process/customer-lifecycle.md` (step 2 and a Changes row), `docs/api/endpoints.md`, `CHANGELOG.md`. Branch `feat/property-edit-new-area`, off `main`.
- **Why:** Mason, hand-testing the customer lifecycle: the property edit page only listed existing areas, so a new area meant leaving the page to make one at `/staff/areas`. He then asked for the field to appear only when no area is chosen and for the option to read "No area/Other".
- **Decisions:** (1) A typed name replaces the list choice rather than being refused as ambiguous, so the page works with no JavaScript. (2) The area is made only after the whole form validates, so a bad ZIP leaves no stray area. A taken name (`Area.create` returns null) is a 400 with nothing changed. (3) The field is hidden and also disabled by `public/js/propertyArea.js`, so a name typed before choosing a listed area is not posted. The field stays visible when scripts do not run, the same rule as `public/js/rebooking.js`. (4) `newAreaName` goes in the `EDITABLE` map so the form and the route share one source of truth. (5) No audit-log entry: creating an area on `/staff/areas` is not logged either.
