## Stage Again for a stranded Messenger batch

- **Changed:** `src/models/messengerBatch.js` (new `stageAgain`; the insert body of `stage` moved into `insertBatch(client, ...)`), `src/routes/messengerBatches.js` (`POST /staff/messenger-batches/:id/stage-again`), `src/controllers/messengerBatches.js` (`stageAgain`, `renderShow`, `renderCreated` takes `fromBatchId`), `src/views/staff/messenger-batch.ejs` and `messenger-batch-created.ejs`; tests in `tests/messengerBatch.test.js` (7) and `tests/messengerBatchPages.test.js` (7); `docs/process/customer-lifecycle.md`; `CHANGELOG.md`. Branch `feat/messenger-stage-again`, off `main`.
- **Why:** Mason found a batch showing 0 sent, 0 failed, 0 skipped that staff could not retry: only a token hash is stored, Messenger must open the link within 60 minutes, and after that `fetchBatch` gives not_found. The request came through the session that started this one.
- **Decisions:** (1) A new batch, not a rotated token on the old one: the old row stays a true record, the new one gets fresh fetch and results windows, no migration or ERD change. (2) The old batch's `fetch_expires_at` is set to `LEAST(fetch_expires_at, now())` in the same transaction, so two live links never exist for the same people; its results window is left alone so late reports still land (and "sent" stays final there). (3) Included `skipped` as well as failed and pending (Mason, yes). (4) Double-text risk: pending recipients are the ambiguous ones, so a warning plus a required checkbox appears only when any are pending, and the model returns `needs_confirmation` without `confirmUnreported`, so a forged POST cannot skip it. (5) The old batch row is locked `FOR UPDATE`, which makes two simultaneous requests run one after the other, not one refused: both can succeed and make two new batches for the same people, because the second still finds them not sent. The lock keeps the recipient read, the insert and the window closing from interleaving, nothing more. A refresh of the created page also stages another batch, as before. Neither is guarded. (6) No `restaged_from` column: the created page shows the source batch, but the link between the two batches is not stored.
- **Open / next:** Nothing is stored linking the new batch to the old one, so the batch list does not show it; add a column if staff ask. Both batches may list the same customer, and Messenger does not know that. The tests ran against `TEST_DATABASE_URL` from the main checkout's `.env` (the worktree has none).

## Stage Again guard against a second batch (PR 96)

- **Changed:** `migrations/035_messenger_batch_restaged_from.sql` (`messenger_batches.restaged_from`, unique, self-reference, SET NULL); `docs/architecture/database-erd.md` (regenerated with `pnpm erd`) and `RouteMaster-Database-Schema.md`; `src/models/messengerBatch.js` (`stageAgain` returns `already_staged` with the earlier batch's id before the confirmation check, `insertBatch` takes `restagedFrom`, `list`/`find` return `restaged_from` and `restaged_as`); `src/controllers/messengerBatches.js` (409 with where the first batch went); `src/views/staff/messenger-batch.ejs` (links both ways, no form on a batch already staged again, `data-once` and the script tag); new `public/js/submitOnce.js`; tests in `tests/messengerBatch.test.js` (+6), `tests/messengerBatchPages.test.js` (+3) and new `tests/submitOnceScript.test.js` (3); process doc and CHANGELOG.
- **Why:** Mason asked to guard against a double click staging a second batch, after I corrected my claim that the row lock prevented it. It only serializes requests.
- **Decisions:** (1) Both parts, Mason's choice: the server check (race-proof under the existing row lock, with UNIQUE in the database as the backstop) and the browser script. The server check alone is not enough: on a double click the browser drops the first response and shows the second, so a refusal would hide the only copy of the first batch's link and strand it again. Keeping the second request from being sent is what lets the first response show. (2) The `already_staged` check runs before the confirmation check, so a refresh answers "already staged", not "tick the box". (3) The button is disabled in a later task (`setTimeout`), because a button disabled during its own click is left out of the posted form; `pageshow` resets it when Back restores the page from cache. (4) A batch can be staged again once, but the new batch can be staged again (its id is a different source), for a lost link. (5) The old page keeps its results, and results Messenger reports for it are still not copied to the new batch.
- **Open / next:** **The FigJam ERD copy is not updated** (no Figma session here): add `restaged_from` (nullable FK) to `messenger_batches` and a self-relationship `messenger_batches |o--o| messenger_batches` labelled `restaged_from`, then update the "made on" date in `database-erd.md`. Migration 035 was applied to the test database with `pnpm migrate:test` (and re-run: nothing to apply); production gets it at the Render deploy, and it must be live before this code runs there. A refresh of the older `stage` and `create` posts still makes a second batch; not changed.
